# ASTRO finite binary32 contract, v1

The binary32 workloads use finite IEEE binary32 encodings, with ASTRO's explicit canonical-positive-zero convention. This is not a full IEEE environment: NaNs, infinities, exception flags, directed rounding modes and FMA are not supported. No claim of IEEE certification is made.

Input values are eight hexadecimal digits in a JSON string; the job declares `encoding: binary32-hex`. Endianness in the binary packet/output is little-endian uint32. A hex string denotes the numeric bit pattern, not four byte pairs in file order. Negative zero is valid input; results of arithmetic, and copied resampling zeros, are positive zero. The comparison itself never masks any sign or other bit: returning negative zero where positive zero is expected fails.

Each individual addition, subtraction, multiplication, division and square root is rounded to nearest, ties to even, with gradual underflow. An underflowing operation may correctly round to zero; the verifier accepts no discrepancy from this rounded result. The CPU reference rejects nonfinite inputs and intermediate overflow, zero division and invalid square roots before any GPU command. Workload-defined singular outputs have explicit status words, not NaNs.

The original small-workload CPU oracle uses Python unbounded `Fraction` arithmetic. The v1.17.12 full-stream SPACE references additionally use probed vectorized CPU binary32 and a two-component windowed FFT; their precise operation graph is documented in [SPACE_ZERO_BIT_AMENDMENTS.md](SPACE_ZERO_BIT_AMENDMENTS.md). A square root is rounded by locating adjacent representable positive numbers and comparing the exact square of their midpoint. The GPU is an independent original implementation with normalized uint32 significands, guard/round/sticky bits, `umulExtended`, restoring long division and base-4 restoring square root. It needs neither FP64 nor shaderInt64. Berkeley [SoftFloat](https://www.jhauser.us/arithmetic/SoftFloat.html) documents the established software-arithmetic approach; no SoftFloat code is copied or linked.

Every reduction uses the order specified in the MathSpec. Tuning may change invocation group size and records handled per invocation; it may not reorder a reduction, replace separate multiplication/addition by FMA or substitute approximate reciprocals. A legal candidate is ranked only after full CPU equality before and after its timing. Every new worker input is checked again even when the kernel has a measured profile.

For the FFT, each record is a complete complex transform. Its canonical algorithm is radix-2 DIT with bit-reversed input, stages of size 2 through N and natural-order output. Twiddles are the frozen binary32 table in `science_library/twiddles.py`, with exact cardinal axes. `tools/generate_science_twiddles.py` generates that table using Decimal90 Chudnovsky pi and Taylor series; runtime never calls platform `sin`/`cos`. Source fingerprints bind the table as well as both implementations. A separate NumPy double FFT comparison corroborates the mathematical transform with a diagnostic bound; that test's bound is never used for GPU result acceptance.

The normal-equation straight-line fit is a bounded primitive, not a numerically stable general least-squares solver. Ill-conditioned input can lose accuracy even with identical CPU/GPU bits. N-body acceleration includes positive softening, with gravitational G absorbed into each source's mu. Leapfrog requires correctly staggered caller-provided half-step velocities. The heat step enforces the stated explicit stability range. These modeling and numerical choices remain separate from implementation verification.

Throughput is resident-input output records per second. FFT records contain a full transform; matrix-multiply records contain one matrix entry. Rates from different workloads must not be added, and software-binary32 rates must not be compared to a different historical tolerance contract as if identical work had sped up.

For v1.17.13 ray/triangle workloads, geometric predicates use exact rational/256-bit integer arithmetic between canonical direction normalization and final RN32 distance. They have their own explicit [triangle contract](TRIANGLE_ZERO_BIT_CONTRACT.md); this is not an implicit reassociation of the older per-operation RN32 workloads.
